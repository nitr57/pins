# NINA.Mcp Architecture

`NINA.Mcp` and `NINA.Mcp.Adapter` add an MCP (Model Context Protocol) server to pins, so that AI clients such as Claude Code can read the equipment state and drive the observatory: connect devices, slew, plate solve and center, capture, focus, guide, move the rotator, flat panel and dome, and build, load, start and stop advanced sequences. For planning and diagnosis they also expose an offline catalog search and target planning for a night, the internal guider's statistics, Guiding Coach reports and flight recorder incidents, the pins log, an event feed of what happened (unsafe, device dropped, save failed, guider alerts), a summary of the session's frames and the health of the pins box (clock, disk, temperature, under-voltage); `secure_observatory` shuts everything down for the end of the night or bad weather. Both projects are pins-specific and not part of upstream N.I.N.A.

## Projects

| Project | Responsibility | Depends on |
| --- | --- | --- |
| `NINA.Mcp` | MCP protocol (JSON-RPC 2.0, lifecycle, Streamable HTTP endpoint, sessions, Origin and token checks), background jobs, the tool catalog, the `IPinsObservatory` abstraction, and the pure helpers behind it: `PropertyBags` (DTO to JSON-friendly bag), `PinsLogReader` (backwards log tail) and `NightPlanner` (twilight, transit and windows from sampled altitudes) | BCL and the ASP.NET Core shared framework only; no NINA project, no NuGet package |
| `NINA.Mcp.Adapter` | `NinaObservatory` and `NinaSequenceService`: `IPinsObservatory` on the NINA mediators, image history, autofocus factory, plate solver factory, dome follower, astrometry and sequencer; `AddPinsMcpForNina` | `NINA.Mcp` and the NINA libraries |
| `NINA.Mcp.Test` | NUnit tests of `NINA.Mcp` (protocol, transport, jobs, every tool against a fake observatory) | `NINA.Mcp` |

The protocol subset is implemented by hand instead of using the MCP C# SDK, which keeps `NINA.Mcp` free of dependencies (no license inventory changes) and testable without NINA.

## Runtime

`NINA/Program.cs` already runs an ASP.NET Core `WebApplication` on `0.0.0.0:4782` for the SignalR hubs. The MCP endpoint is mapped on the same host:

1. `McpServerOptions.FromEnvironment(CoreUtil.Version)` reads the `PINS_MCP_*` variables.
2. `builder.Services.AddPinsMcpForNina(options)` registers the server, the tools, the adapter and a log forwarder into the pins log. It registers nothing when the endpoint is disabled.
3. `app.MapPinsMcp()` maps `POST`, `GET` (405) and `DELETE` at `/mcp`.

The adapter's NINA services come from the same service collection (`IoCBindings`). Everything is a lazily resolved singleton, so a broken registration fails the MCP request (500), not the pins start.

Request flow: HTTP → `McpHttpEndpoint` (Origin, token, session, size and header checks) → `McpDispatcher` (JSON-RPC, `tools/list`, `tools/call`) → `ObservatoryTool` (argument validation, sequence guard, job start) → `IJobManager` (background work outliving the request) → `NinaObservatory` → NINA mediators.

## Configuration

| Variable | Default | Effect |
| --- | --- | --- |
| `PINS_MCP_ENABLED` | on | `0`/`false` disables the endpoint completely |
| `PINS_MCP_TOKEN` | unset | Requires `Authorization: Bearer <token>` on every request |
| `PINS_MCP_READONLY` | on without token, off with token | Read-only lists only queries plus `stop_all` and `cancel_job` |
| `PINS_MCP_ALLOWED_ORIGINS` | unset | Extra browser origins (exact scheme://host:port), comma separated |

Set them with a systemd drop-in (`sudo systemctl edit pins`):

```ini
[Service]
Environment="PINS_MCP_TOKEN=<long random string>"
```

Connect Claude Code from a machine in the same network:

```bash
claude mcp add --transport http pins http://<pins-host>:4782/mcp --header "Authorization: Bearer <token>"
```

The endpoint is plain HTTP, so the token can be read by anyone who can sniff the network (an open access point at a star party). Use it on a trusted network, or reach pins through Tailscale or an SSH tunnel (`ssh -L 4782:localhost:4782 <pins-host>`, then `http://localhost:4782/mcp`).

## Contracts

- **Security.** Requests without an `Origin` header (non-browser clients) are accepted. Browser origins must be loopback, a private, link-local or CGNAT (Tailscale) address, a `.local` name, the machine name, or listed in `PINS_MCP_ALLOWED_ORIGINS`; everything else gets 403 (DNS-rebinding protection). Without a token the endpoint is read-only unless `PINS_MCP_READONLY=0` is set explicitly; pins then logs a warning at startup.
- **Protocol.** Versions `2025-11-25`, `2025-06-18` and `2025-03-26`; JSON responses only (no SSE stream); batches only for `2025-03-26` and at most 16 messages, processed concurrently; `Mcp-Session-Id` sessions expire after 24 idle hours (a client typically starts a sequence and returns hours later), at most 1000 are kept. Protocol-level internal errors carry no exception details; those go to the log.
- **Jobs.** Slews, plate solves, centering, captures, cooling, focusing, filter changes, guiding, connections, switches, rotator moves and flat panel and dome commands run as jobs that outlive the request. A tool waits up to `wait_seconds` (default 30, at most 55 to stay below common 60 s client timeouts) and otherwise returns the job id for `get_job`. A job claims one resource (`mount`, `camera`, `camera_cooler`, `focuser`, `filter_wheel`, `guider`, `switch`, `rotator`, `flat_device`, `dome` or a device slot) and may require others to be idle; claim and idle check are one atomic step. Short operations that are not jobs (`set_tracking`, `start_sequence` until the sequence runs) reserve their resources the same way. Mount motion requires the guider idle (slew and home also the camera); capture, autofocus and plate solving require the mount, rotator and flat device idle. `plate_solve` holds the camera; `center_target` holds the mount, requires camera, guider, filter wheel, focuser, rotator and flat device idle, and reserves camera, guider and filter wheel from inside its job until it ends or is cancelled (a job claims one resource; the reservation keeps captures, filter, focuser, rotator and flat moves and guiding starts out between its exposures, camera and guider are released on the cancel request so that an abandoned job cannot keep them; the filter wheel when the work returns, at most six minutes after the cancel, because NINA's centering solver restores the filter on a fresh token). A guiding start requires the mount idle. Rotator moves and flat device commands require the camera idle. Dome commands require nothing idle, so closing the dome is never blocked by another job. Cancelling a job cancels its token, which halts the hardware operation; failing halts are reported by `cancel_job` and `stop_all`. A job whose work ignores the token stays running with `cancelRequested`, and `cancel_job` with `abandon: true` ends it as `abandoned` and releases its resource. At shutdown pins cancels every job and waits up to five seconds before disconnecting equipment.
- **Sequence guard.** While the advanced sequence runs, hardware and editing tools are refused unless `force: true` is passed; `load_sequence`, `clear_targets`, `reset_sequence` and `start_sequence` are always refused. `start_sequence` is also refused while an MCP job holds hardware. `stop_all` is never refused.
- **Adapter rules.** Expected failures are returned as `OperationResult`, not thrown. Results are verified against the device state where NINA does not report failures (tracking, filter position, switch value). An idle mount gets no abort command, because some drivers stop tracking on abort; a slew, park or home started over MCP counts as moving from the moment it is sent, because the cached `Slewing` flag lags by a polling interval. Park and home stop guiding first, like their sequence instructions. Capture and autofocus hold the camera capture block (as the flat wizard, framing and snapshot tools do) unless the advanced sequence runs. Captures are stretched and star-detected with the profile's image settings, like sequence light frames. Plate solving and centering use the profile's plate solve settings and NINA's capture and centering solvers like the SolveAndSync and Center instructions (centering stops guiding first and restarts it, inside the job, once the slew succeeded; cancelling it aborts the exposure and the solver, and the mount gets an abort only while it reports slewing), and hold the camera capture block like captures. Results are verified against the device state where NINA does not report failures: flat device state, dome park, home, azimuth and shutter end state. Cancelling a dome job stops the dome like NINA's dome stop command (follower, following, device; the INDI dome only stops waiting otherwise), but never a shutter that is closing, which is NINA's own close. Closing the shutter never sees a job's token: it runs on a ten-minute token of its own and cancelling only ends the wait, because `stop_all`, `secure_observatory` and the pins shutdown cancel every job and ASCOM/Alpaca abort the shutter on cancellation. `secure_observatory` treats a disconnected mount as not parked and only counts a dome that reports its shutter closed. Find home waits for the rotation to end, because the INDI dome returns at once. A sky-angle rotator move needs a synced rotator. Loading a sequence clears NINA's save path, so NINA's Save cannot overwrite the previously loaded file; linked templates are refreshed on load and materialized before the start validation, as NINA does on start. Model-facing numbers are formatted with the invariant culture.
- **Diagnostics data.** Guider data comes from the internal guider's `IAdvancedGuider`, `IGuidingCoach` and `IGuideIncidentRecorder` contracts and reaches the tools as property bags (`PropertyBags`), so `NINA.Mcp` needs no reference to the DTOs; raw coach samples and per-frame star lists are left out unless asked for, incident images never leave pins. Coach reports and incidents stay readable while the guider is disconnected: the guider mediator only knows a connected device, so the adapter falls back to the internal guider singleton (`IAdvancedGuider` in `IoCBindings`) while no other guider is connected and the profile's guider is the internal one. Other guiders only report state and RMS.
- **Log.** `read_log` reads the current run's log file (the `.log` in `~/.local/share/NINA/Logs` this process holds open, found through `/proc/self/fd`, with the process id in the file name as fallback; systemd often reuses process ids across boots) or the previous run's (the newest other file), backwards from the end with a byte budget (32 MB), so it is cheap on a long night log. Levels, text and age filters apply while scanning; the result says how much was scanned.
- **Planning.** `plan_targets` samples one observing night (24 hours from the site's mean solar noon, 12:00 UTC − longitude/15, moved back to the box's full local hour; 5-minute steps; see `NightWindow`) at the profile's site, so a box time zone far from the site's does not shift the night (the result notes such a box offset): target altitude and azimuth with NINA's SOFA transform (no refraction), sun and moon with NOVAS, the custom horizon at each azimuth. `NightPlanner` derives twilight, dark hours, transit, limit crossings (linear interpolation between samples), usable dark hours and the longest window; resolution is the sampling step.
- **Events.** `ObservatoryEventLog` (in `NINA.Mcp`, registered with the tools) keeps the last 2000 events with increasing ids (when full, the oldest event of the lowest severity goes first, so a flood of info events cannot push out a critical one; the bridge reports at most one incident save per minute); `get_events` reads them by cursor (`since_id`) and long-polls up to 55 s. The adapter's `NinaEventBridge`, a hosted service started with the web host, subscribes to the mediator events (safety while the monitor is connected, including a monitor that is already unsafe when it connects, meridian flip, park, guiding start/stop, download timeout, image saved/failed, sequence start/end once the sequencer is initialized) and the internal guider's alerts and incidents. Device connections are polled every three seconds: several VMs raise Disconnected at the start of every connect and a dropped device raises no event, so a connection that ends without a Disconnected event around it (judged one poll later, because VMs mark the info disconnected before raising the event) is reported as lost (error). The rules live in the pure `DeviceConnectionTracker`: a Disconnected event only counts while the device was connected, and the guider VM's own Disconnect after its device dropped (seen as a broadcast that turns the guider disconnected while the VM still holds the device) is a lost connection, not a request. Polling stops when pins begins shutting down. Each run starts its event ids above every earlier run's (four per second since 2025), so a cursor from before a restart is reported as missed instead of hiding the new run's first events. Because those ids come from the wall clock, which can go back on a Pi without network time or RTC battery, every run also has a random `runId` that `get_events` returns and accepts as `run_id`; a cursor with another run's id reads from this run's start and reports missed. Each subscription is optional and nothing in the bridge can fail the pins start or throw into a mediator.
- **Sequence safety.** A target built by `add_target` from an exposure plan gets NINA's meridian flip trigger (`meridian_flip`, default true), with the profile's flip settings, like NINA's target templates. Without a connected mount it is left out (its validation would refuse the start), and the result says so.
- **Catalog.** `find_targets` queries the sky atlas database (`DatabaseInteraction.GetDeepSkyObjects`) on the pins box, so coordinates are available without internet.
- **Session and health.** `get_session_summary` aggregates the in-memory image history of this run (it starts empty after a restart). `get_system_health` reads `/proc`, `/sys`, `vcgencmd get_throttled` and `timedatectl` with a two-second timeout per command; every reading is optional, and the clock error is measured against a time the client passes. The mount's time is reported as last published (INDI drivers may only send it at connect), without a clock warning.
- **Shutdown.** `secure_observatory` stops the sequence, cancels all jobs and aborts the exposure before it starts its own job (so it cannot cancel itself); in the job it waits up to ten seconds for the cancelled jobs, reserves every device (best effort) so that nothing can unpark or open in between, stops guiding, parks, closes the dome only when the mount is parked, closes the dust cover and optionally warms the camera. It claims no resource and has no sequence guard, but unlike `stop_all` it moves hardware and is therefore not available in read-only mode.
- **Upstream merges.** The only edits to existing upstream files are one `ProjectReference` in `NINA/NINA.csproj` and the solution entries; the wiring lives in the pins-only `NINA/Program.cs`.

## Verification

`NINA.Mcp.Test` covers `NINA.Mcp` completely through the fake observatory, including HTTP tests against a real Kestrel host. `NINA.Mcp.Adapter` is compiled with `NINA/NINA.csproj`; its behavior depends on real devices and is verified on hardware or with the device simulators.

## Not Exposed Yet

Candidates for later tools, with the NINA code that already does the work:

- **More sequence safety for MCP-built targets.** No unsafe trigger and no stop condition (dawn, altitude) yet: `TriggerOnUnsafe`, `SunAltitudeCondition`, `TimeCondition`, `AltitudeCondition`. A condition on the target container makes NINA loop the whole target while it holds, so stop conditions need their own container design.
- **Push.** Events are polled (`get_events` long-poll); there are no MCP notifications (JSON-only responses, GET returns 405), and job completions are not events yet (finished jobs expire from `list_jobs` after an hour).
- **Images.** Tool results are text only; an MCP image content of a stretched thumbnail (`IRenderedImage.GetThumbnail`) would let a multimodal client judge clouds, gradients and star shapes.
- **Sequence editing** beyond `add_target`/`clear_targets`: remove, move, enable/disable, skip and change counts by path (the snapshot already addresses items by path), triggers such as `AutofocusAfterHFRIncreaseTrigger` and `CenterAfterDriftTrigger`.
- **Guider control.** `IAdvancedGuider` settings, looping, star selection and dark library; `IGuidingCoach.StartCoach`/`ApplyCoachActions`; `IGuideIncidentRecorder.MarkIncident`.
- **Meridian flip and dither** outside a sequence (`IMeridianFlipVMFactory`, `IGuiderMediator.Dither`).
- **Flats** through the sequence items `AutoExposureFlat`, `AutoBrightnessFlat`, `TrainedFlatExposure`, `SkyFlat`.
- **Profile settings** read/write with an allowlist (`IProfile` sections, filter focus offsets, meridian flip settings).
- **Camera and focuser configuration** (readout mode, USB limit, dew heater, image type for darks and bias, relative focuser moves, temperature compensation).
- **INDI diagnostics** (`INDIClient.GetMessages`, device snapshots) and device selection.
- **Protocol**: `outputSchema`, prompts (start night, morning report), `notifications/cancelled`, resources, progress notifications over SSE.
